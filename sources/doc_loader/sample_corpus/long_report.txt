Retrieval System Design Notes

This report walks through the design of the ingestion and retrieval pipeline built for the document search project. It covers the loading stage, the cleaning stage, and the chunking stage, and explains the reasoning behind each choice. The goal throughout has been to keep every stage simple, inspectable, and free of hidden network dependencies so the whole pipeline can run offline during development and testing.

The loading stage reads PDF, plain text, Markdown, and HTML files from a folder and converts each one into a single plain-text string. PDF pages are extracted one at a time and joined with newlines. HTML files have their script and style tags removed before the remaining visible text is pulled out. Plain text and Markdown files are read directly without any reformatting, since their content is already close to what the retrieval system needs.

The cleaning stage takes that raw text and makes it consistent across every source format. It normalizes Unicode so visually identical characters compare equal, repairs a handful of common encoding artifacts, and unifies line endings so downstream code never has to branch on whether a file came from Windows or Unix. Repeated running headers and footers, such as page counters, are detected and removed so they do not pollute every chunk with the same boilerplate line. Runs of blank lines and repeated spaces are also collapsed down to a single blank line or a single space, which keeps chunk boundaries from landing on meaningless whitespace.

The chunking stage is where the cleaned text gets cut into pieces small enough to embed and retrieve individually. Two different strategies are implemented here so their trade-offs can be compared directly on the same input. The first strategy cuts the text into fixed-size windows measured in characters, with a small overlap between consecutive windows so that a sentence sitting on a boundary is not lost entirely from either chunk. The second strategy respects the paragraph structure of the document, grouping whole paragraphs together up to a size limit, and only falling back to splitting a paragraph by sentence when a single paragraph is larger than that limit on its own.

Fixed-size chunking is attractive because it is trivial to implement, its output sizes are extremely predictable, and it works even on text that has no discernible paragraph structure at all, such as a wall of OCR output or a transcript with no line breaks. Its weakness is that the cut points are arbitrary with respect to meaning, so a chunk can start or end mid-sentence, which can hurt both the quality of the embedding for that chunk and the readability of the snippet shown back to a user during retrieval.

Paragraph-based chunking is attractive for the opposite reason: because it respects the author's own structure, each chunk tends to correspond to one coherent idea, which usually improves both embedding quality and the readability of retrieved snippets. Its weakness is that paragraph lengths vary a lot between documents and even within a single document, so the resulting chunk sizes are less uniform, and a document with no paragraph breaks at all degrades toward one enormous chunk unless the sentence-level fallback kicks in.

For a real corpus made up of normal prose documents with visible paragraph structure, such as reports, articles, and documentation pages, paragraph-based chunking is the better default because retrieval quality benefits more from semantically coherent chunks than from perfectly uniform chunk sizes. Fixed-size chunking remains useful as a fallback for the minority of documents that have little or no paragraph structure to lean on, or as a safety net inside the paragraph strategy itself when an individual paragraph turns out to be unusually long.
